# What You Gain + Build With Us: Icon-Graphic Redesign

## The Problem

The "What You Gain" section (`index.html:215-285`) and "Build with us" section (`index.html:325-358`) are both plain-text sections that don't reflect the "more visually pleasing" bar the rest of the redesigned site has. The builds section right before gains already has a numeral watermark (`.build-num`, `css/home/redesign.css:634`) and a real image card (`.build-art img`, `css/home/redesign.css:678-682`), but Gains is 4 sequential full-viewport-height (`min-height: 46vh`) list rows the user scrolls through one at a time, each triggering its own ink-fill headline + leader-line + staggered-copy animation — three animations firing per row across 4 rows was described as "a pain on the eyes with all the movement," and the total scroll distance (4x 46vh+ minimum) doesn't fit on screen together. Join's role cards (`.role-card`, `css/home/redesign.css:934-937`) are just `border-top: 2px solid var(--ink)` with a heading and paragraph — no icon, no card body, no visual distinction from plain body text ("just text on the background"). Both need a graphic treatment instead of the current typography-only approach, without regressing to a heavy asset pipeline the vanilla-JS/Vite site doesn't have (no icon font, no illustration library, one PNG mascot in `assets/`).

## The Technical Plan

Two sections, one shared icon system, two different layout patterns.

**Shared foundation: inline SVG line-icon set.** 6 new icons, hand-authored directly as inline `<svg>` markup inside `index.html` (no new asset files, no icon font/library dependency) — 3 for gains nodes, 3 for join roles. Style: single-color line strokes (`stroke="currentColor"`, no fill), 1.5px stroke-width in each icon's own viewBox units, with `vector-effect="non-scaling-stroke"` on every icon's stroked path/line elements so the stroke stays visually ~1.5px regardless of the icon's final rendered size (icons render at different sizes depending on context/breakpoint — without `non-scaling-stroke`, the stroke would scale with the icon and stop matching intent). Each hand-authored `<svg>` must include a `viewBox` attribute matching its own coordinate system, not just `width`/`height` attributes — required for the CSS sizing technique below to scale the icon proportionally rather than stretching or clipping it. All 6 icons additionally share the same viewBox aspect ratio (a square, `0 0 24 24`) — since `--gain-icon-h` (below) fixes every icon's rendered height to the same value, and the default `preserveAspectRatio` behavior letterboxes any icon whose intrinsic aspect ratio doesn't match its box, icons authored at differing aspect ratios would render at visibly inconsistent effective sizes side by side despite sharing an identical wrapping box. This mandate solves *geometric* sizing consistency only — it doesn't by itself guarantee the 6 hand-drawn icons read as equally visually "heavy" or occupy proportionally similar space within their shared square (a two-person outline and a megaphone can be geometrically identical in bounding box while looking optically mismatched in weight) — that's a hand-eye design-craft judgment left to whoever draws them, not something a spec can fully mechanize.

Sized via CSS: a wrapping `<span class="gain-icon">`/`<span class="role-icon">` gets a fixed `width`/`height`, with `width` set equal to `height` in both cases (`.gain-icon` uses `var(--gain-icon-h)` for both; `.role-icon` uses its own independently-chosen equal width/height pair — see below for why it isn't tied to `--gain-icon-h`) — this equality is required, not a free styling choice: a non-square wrapper span would letterbox/pillarbox the square icon artwork inside it via the same `preserveAspectRatio` mechanism the square-viewBox mandate above exists to avoid, just relocated from icon-vs-icon inconsistency to wrapper-vs-icon inconsistency. Plus a nested `.gain-icon svg`/`.role-icon svg { width: 100%; height: 100%; display: block; }` rule (sizing the span alone doesn't shrink an inline `<svg>` carrying its own width/height attributes; `display: block` is required too — an unstyled `<svg>` defaults to `display: inline`, the same default a plain `<span>` has, carrying the same baseline-alignment whitespace gap that motivates the classic `img { display: block }` reset; without it, a few stray px of gap can appear beneath the icon inside its otherwise correctly-sized wrapper). Both wrapping spans must also get `display: inline-block` — a plain `<span>` defaults to `display: inline`, and `width`/`height` are ignored by the CSS spec on non-replaced inline boxes, so without this the span would never actually take the fixed height at all, silently no-opping the sizing rule. This file already has exactly this pattern solved correctly once: `.badge` (`css/home/redesign.css:155-156`) sets `display: inline-block` before applying sized/bordered/padded styles to a similar wrapper — `.gain-icon`/`.role-icon` follow that same precedent. Both `.gain-icon` (sitting before `.gain-kicker`) and `.role-icon` (sitting before its `<h4>`) also need an explicit `margin-bottom` for the same reason: the sitewide `* { margin: 0 }` reset (`css/home/redesign.css:22-26`) leaves icon and following text flush with no gap otherwise. This applies identically to both — gains nodes and role cards have the exact same icon-then-text adjacency.

`.gain-icon`'s fixed height is set via a CSS custom property, `--gain-icon-h`, rather than a hardcoded literal repeated in multiple places — it's referenced by `.gain-icon { height: var(--gain-icon-h); width: var(--gain-icon-h); }`, the dot's `top` calc, and the connector's `margin-top` calc (both below), so all three stay in sync if the icon size is ever tuned later. Declared once, on `.gain-graphic` (or `:root`, implementer's call which). This variable is gains-only — `.role-icon`'s own size is an independent value with no shared numeric token between the two sections; "shared icon system" (above) refers to the shared SVG-authoring technique (inline markup, span-wrapper sizing, `non-scaling-stroke`), not a shared size constant. This value is a single fixed constant reused unchanged at both breakpoints, not a fluid `clamp()` value like the site's headline type (`.section-title`, `.hero-title`, `.story-line`, etc) — a deliberate choice: responsiveness here comes from the grid reshaping (3-col → 1-col), not from the icon itself scaling, and a small fixed-size decorative UI glyph doesn't carry the same legibility-driven need for fluid scaling that running headline text does. This value also has an implicit constraint symmetrical to `.gain-node-copy`'s explicit "2 lines" constraint (below): whatever `--gain-icon-h` is chosen, it must render comfortably within whichever tier's column is actually narrowest — here that's the shared 3-column tier (everything from 768px up, per the unified grid below), not the single-column mobile tier, since three columns splitting the section's content width is the tighter constraint than one column getting the full width; not stated as a hard number here, but implementer must sanity-check it against the real `--gutter`/column-gap values the same way the copy-fit constraint is checked.

Colored `var(--ink)` by default — via inheritance from the sitewide `body { color: var(--ink) }` rule (`css/home/redesign.css:39`), not a `color` property set directly on `.gain-icon`/`.role-icon` themselves; nothing between `<body>` and either icon span overrides text color, so no explicit declaration is needed for this to hold. Icon-to-node/role mapping, explicit (each maps to one specific node/card by index, not left to be inferred from theme-matching alone):
- Gain node 1 (Lean Team): two-person outline icon.
- Gain node 2 (Full Ownership): checkmark-in-box icon.
- Gain node 3 (Shipped Product): screen-with-checkmark icon.
- Join role card 1 (Developers): code-bracket icon.
- Join role card 2 (Designers): paintbrush/pen-nib icon.
- Join role card 3 (Strategists): megaphone icon — matches "Drive marketing and product decisions" copy better than a bar-chart, which reads as generic analytics/data rather than marketing.

Accessibility: `aria-hidden="true" focusable="false"` goes on each `<svg>` itself (not the wrapping span — a plain `<span>` isn't announced or focusable by default, so hiding it too is redundant). The `aria-hidden="true"` half matches the existing decorative-element convention already used elsewhere in this file (`.progress-bar` at `index.html:28`, `.build-num`, the old `.gain-leader`) exactly. `focusable="false"` has no prior precedent in this file — none of those existing decorative elements are `<svg>` — but is the correct, standard addition for SVG-specific decorative-hiding (SVG elements have historically had inconsistent default focusability across browsers, unlike span/div). Decorative icons sitting beside redundant visible text must not add screen-reader noise.

**Gains: 3 full-viewport rows become one connected-progression graphic.** Replace `<ol class="gain-list">` of `<li class="gain-row">` with `<div class="gain-graphic">` (this is now the CSS Grid container — see Connector below for why) holding a `<ul class="gain-nodes" role="list">` (switched from `<ol>` — see Alternatives for the caveat on this rationale and why `role="list"` is present; also gets `display: contents;`, explained below) of 3 `<li class="gain-node">` (each needs `position: relative; min-width: 0; padding-left: 1rem;` — `position: relative` so its `::before` dot positions against the node itself, not some ancestor; `min-width: 0` because a grid item's implicit `min-width: auto` otherwise stops it shrinking below its text's natural width, which matters for the copy-wrapping treatment below; `padding-left: 1rem` reserves a dedicated left-side gutter for the dot and, at mobile, the connector's vertical rail — see Connector below for why this replaced an earlier negative-offset-only approach). `.gain-graphic` originally carried forward the old `.gain-list`'s `margin-top: clamp(3rem, 8vh, 5rem)` separating it from the `<h2 class="section-title">` above, unchanged. A later density-scale-down pass ("Scale down the gains and role-card sections to match main's density") retuned it to `clamp(2.25rem, 5vh, 3.5rem)` (`css/home/redesign.css:760`) to match the rest of the page's tightened vertical rhythm — no longer the untouched pass-through value it started as. Each node, in this order: icon (fixed-height), a mono kicker line, a plain `<h3 class="gain-node-title">` headline (keeps the existing `<h2>` section title → `<h3>` per-item heading hierarchy the current `<h3 class="gain-node-title">` already establishes at `index.html:243`; drops the stroke/fill double-layer ink-fill trick, since breaking from the blueprint identity here was explicitly approved), and one line of copy — final content, verbatim from `index.html`:
- 01: kicker "01: Lean Team", title "Lean Team.", copy "Teams of 3–4, led by an experienced builder."
- 02: kicker "02: Full Ownership", title "Full Ownership.", copy "Portfolio-ready products used by 500+ Hopkins students."
- 03: kicker "03: Shipped Product", title "Shipped Product.", copy "Final presentation to the club and beyond."

`.gain-node-title`'s text is, for all three nodes, a literal duplicate of its kicker text minus the numeral prefix ("01: Lean Team" → "Lean Team.", etc) — accepted as intentional redundancy, the same eyebrow-label convention already acknowledged elsewhere in this doc, not an oversight. This redundancy is visual/sighted-user reasoning; screen readers get no equivalent filtering — a screen reader will read both `.gain-kicker` and `.gain-node-title` back-to-back per node (e.g. "02: Full Ownership. Full Ownership.") since neither is `aria-hidden` the way the decorative icon is. Accepted: this is a mild redundancy, not a broken or missing-information experience, and matches what sighted users see too — but it's a deliberate accept, not an unconsidered gap.

`.gain-node-title` carries forward the old `.gain-line`'s font-family (`var(--font-display)`) and weight (600) — only its `clamp()` font-size is replaced with a smaller one. This went through two rounds: a mean-review pass first collapsed it to a flat, non-fluid `1.1rem` at the shared base tier and `1.75rem` under the `max-width: 767px` mobile override, to kill an exact-pixel-match zoom-truncation risk at the tablet width (see below); a later density-scale-down pass then reintroduced fluid scaling at a smaller range, shipping as `font-size: clamp(1.05rem, 1.7vw, 1.35rem)` at the shared base tier and `font-size: 1.5rem` under the mobile override (`css/home/redesign.css:825,883`). The zoom-truncation risk the flat-value fix addressed has not been re-verified against this reintroduced clamp — flagged here as an open follow-up, not confirmed safe. Unlike the old draft's tier-stepped scheme, there's no counter-intuitive "narrower tier gets bigger type" trap to watch for here: desktop and tablet now share one unqueried grid, so the only step is base → mobile, and mobile's single-column layout genuinely has more horizontal room per title than the shared 3-column tier does, so bigger type there is the expected direction, not a surprise. It also gets `white-space: nowrap; overflow: hidden; text-overflow: ellipsis;` — defensible since each title is 1-2 words ("Lean Team.", "Full Ownership.", "Shipped Product.") and fits one line at either tier's column width even under moderate zoom. At browser zoom approaching WCAG 1.4.4's 200% bar, these short titles could still truncate to an ellipsis in a narrow column — accepted, since the adjacent, non-truncated kicker line conveys the same concept in full immediately next to it (kicker and title are literal duplicates for all three nodes, per above); no information is actually lost even if the title glyph-truncates. `.gain-node-title` also needs an explicit `margin-bottom` separating it from the `.gain-node-copy` paragraph directly below it — the same sitewide `* { margin: 0 }` reset (`css/home/redesign.css:22-26`) that motivates `.gain-icon`/`.role-icon`'s `margin-bottom` (above) applies here too; left unset, title and copy render flush against each other. `.gain-node-copy` carries forward the old `.gain-note-copy`'s `color: var(--slate)`, unchanged. It does NOT get the nowrap/ellipsis treatment: design review found the actual final copy above — e.g. "Portfolio-ready products used by 500+ Hopkins students." at roughly 58 characters — does not fit on one line at either tier's column width, so a nowrap/ellipsis rule would silently truncate real, final marketing copy. Instead, `.gain-node-copy` wraps normally and gets a fixed `min-height` (2 lines' worth, at its own line-height) so nodes with 1-2 lines of wrapped copy reserve consistent vertical space. This is a floor, not a guaranteed cap: if the eventual chosen column width/font-size (both still open implementer calls, see below) ever forces a node's copy past 2 lines, that node's box grows past the shared `min-height`, and — since this grid's items default to `align-items: stretch` — the whole row stretches to match, leaving shorter-copy siblings in that row with extra space beneath them rather than a hard misalignment. Icon/dot/connector alignment (all anchored from the top of each node) is unaffected either way. Implementer must pick a column width/font-size combination where all 3 sentences above actually fit within 2 lines — this is a real constraint on the still-open sizing decisions, not just a cosmetic preference. The width being tested here is the usable text width, not the raw grid-column track width: `.gain-node`'s `padding-left: 1rem` (above) insets all content including the copy, so the actual wrapping width available to `.gain-node-copy` is the column's track width minus `1rem` — sizing font/column-width against the full track width would overestimate available space, most likely to matter at the shared 3-column tier. Node 2's copy ("Portfolio-ready products used by 500+ Hopkins students.") is the binding constraint on this fit exercise, not just an average-case sentence — it's the longest of the 3 sentences, so verifying the fit against node 2 specifically is what actually confirms the chosen combination works. (`.gain-node`'s `min-width: 0` from above still matters here too — it's what lets the reserved-height copy actually wrap within its own column instead of overflowing the grid track.) None of the three copy lines use bold `<strong>` emphasis — the earlier draft's course-credit copy did, but that copy (and the node it belonged to) was cut in a later revision along with the featured-node treatment below.

Layout has two tiers, structured as an unqueried base with a single `max-width: 767px` override layered on top — matching the cascade pattern every other breakpoint in this file already uses (`css/home/redesign.css` has no `min-width` media query anywhere; every existing breakpoint is a `max-width` override cascading down from an unqueried base). An earlier draft split desktop and tablet into two separate tiers (a 4-column base and a 2-column `max-width: 1023px` tablet override); a follow-up revision found the 4-column desktop layout didn't hold up and unified desktop and tablet into one shared 3-column grid instead, dropping the tablet-specific tier entirely. What ships is the simpler two-tier version below.
- **Base** (the unqueried default — `.gain-graphic`'s default state, everything ≥768px): 3-column grid (`grid-template-columns: repeat(3, 1fr)`, `css/home/redesign.css:761`). No explicit height/min-height target is set on `.gain-graphic` — its actual rendered height is whatever the 3 nodes' content (icon + kicker + title + copy) produces. One connector line spans all 3 nodes, left to right.
- **Mobile** (`@media (max-width: 767px)`, overriding the base): single column, 3 stacked rows. Connector becomes one continuous vertical line down the left edge, through all 3 nodes in order.

(This is the same `max-width: 767px` breakpoint value used everywhere else in this file — the only breakpoint value gains needs, now that desktop and tablet share one grid.)

**Connector: a CSS Grid sibling, not an absolutely-positioned overlay — with explicit placement for both the connector AND the nodes, all defined in the base/override structure above.** Earlier drafts of this doc had `.gain-connector` positioned absolutely inside `.gain-graphic`, with dots (`.gain-node::before`) aligned to it via matching `top` offsets computed independently. Design review found real problems with that approach and with a subsequent revision, resolved as follows.

`.gain-graphic` is the CSS Grid container, with BOTH `grid-template-columns` AND `grid-template-rows` set explicitly at every tier (base and both overrides) — an explicit row template at every tier is what makes the mobile connector's row-span (below) resolve correctly. `.gain-nodes` (the `<ul>`) gets `display: contents; list-style: none;` — the `list-style: none` must be explicitly carried over here: `display: contents` does not itself suppress the browser's default list markers on the `<li>` children (a documented `display: contents` gotcha, not automatic); the old `.gain-list` had `list-style: none` for this exact reason — that declaration now lives on `.gain-nodes` (`css/home/redesign.css:768`) and it must not be silently dropped. `display: contents` makes the `<li>` children participate directly as grid items of `.gain-graphic`'s grid, without making the connector elements invalid non-`<li>` children of a `<ul>` (they live as siblings of `.gain-nodes` inside `.gain-graphic`).

CSS Grid's auto-placement algorithm reserves cells claimed by fully-definite `grid-column`/`grid-row` items *before* placing any auto-positioned items, and skips cells already marked occupied — so every grid item here, on every tier, needs explicit placement; nothing can be left to auto-place, or it silently gets shoved into a new implicit row/column instead of sharing space with the explicitly-placed items. This applies to `.gain-node` (fixed in the previous revision) and, before the desktop/tablet unification above, had also tripped up an earlier two-connector draft: a secondary connector element intended only for the tablet tier needed an explicit `display: none` in the base (desktop) state or it would auto-place as a stray grid item there. That secondary connector no longer exists in the shipped design — desktop and tablet share the one `.gain-connector-primary` element (see Connector below) — so this failure mode doesn't apply anymore, but it's the reason every grid item here still gets explicit placement on every tier rather than being left to auto-place.

`.gain-node` gets explicit `grid-column`/`grid-row` placement via `:nth-child`, at every tier:
- Base: `grid-template-columns: repeat(3, 1fr); grid-template-rows: auto;` — `.gain-node:nth-child(1) { grid-column: 1; grid-row: 1; }` through `:nth-child(3) { grid-column: 3; grid-row: 1; }` (`css/home/redesign.css:761-762,778-791`).
- Mobile override: `grid-template-columns: 1fr; grid-template-rows: repeat(3, auto);` — `:nth-child(1) { grid-column: 1; grid-row: 1; }` through `:nth-child(3) { grid-column: 1; grid-row: 3; }` (`css/home/redesign.css:867-880`).

This explicit `:nth-child`-per-tier scheme is intentionally hand-maintained, not automated — adding, removing, or reordering a gain node would require updating placement rules across both tiers by hand, with nothing enforcing consistency. Accepted: the node count (3) and order are fixed content decisions, not expected to change, and this explicitness is what fixes the CSS Grid auto-placement bug class (above) in the first place — the alternative (auto-placement) is the thing being deliberately avoided.

One connector element exists in the markup, `.gain-connector-primary` — a single class, no base-plus-modifier pair. An earlier draft carried a second `.gain-connector-secondary` element for a two-row tablet layout with its own connector segment; once desktop and tablet were unified into one 3-column grid (above), that second row — and the element that drew a connector across it — no longer had anything to attach to, so it was dropped along with the tablet-specific tier.

Each connector element's placement, by tier:
- Base: `.gain-connector-primary { grid-column: 1 / -1; grid-row: 1; }` (shares row 1 with all 3 nodes, `css/home/redesign.css:848-849`).
- Mobile override: `.gain-connector-primary { grid-column: 1; grid-row: 1 / -1; align-self: stretch; justify-self: start; width: 1.5px; height: auto; }` — spans all 3 explicit rows via line `-1` (`css/home/redesign.css:889-896`); `justify-self: start` is set explicitly for clarity, though likely redundant in practice — once `width` is a definite (non-`auto`) value, CSS Box Alignment's default `justify-self: normal` already behaves equivalently to `start` for a grid item; unlike the `height: auto` reset (which is load-bearing, see below), this one is a low-stakes belt-and-suspenders declaration, not a fix for an actual bug.

Mobile connector's bottom terminus is intentionally NOT capped at node 3's dot. `align-self: stretch` on `grid-row: 1 / -1` means the connector's rendered bottom edge lands at the grid area's bottom line — the bottom of node 3's full content block (icon + kicker + title + copy), not at node 3's dot specifically. Capping it exactly at node 3's dot would require knowing node 3's exact content height in advance, the same JS-measurement dependency the CSS Grid approach was adopted specifically to avoid (see Alternatives) — row 3's height varies with wrapped copy length, so no fixed `margin-bottom` calc can land precisely on it the way the top's fixed `margin-top` calc lands on node 1's dot. Accepted: the connector's job is establishing a continuous visual rail down the left edge through all 3 nodes in sequence, not a precise joint-to-joint line terminating at exactly 3 points; running past the last dot and ending flush with the bottom of node 3's content instead is a fine visual outcome for that goal, and is consistent with this doc's existing tolerance for similar minor decorative imperfections elsewhere (off-screen draw completion, forced-colors remapping). The same acceptance applies to the base tier's connector right edge: `grid-column: 1 / -1` extends its line all the way to the grid container's own right edge, which — since each node's own icon/text content is narrower than its `1fr` column — visibly runs past the last node's own icon before stopping. This is flush with a real, deliberate boundary too (the row's own right edge, i.e. the section's content width), not a random empty cutoff — the same class of acceptance as the mobile bottom-terminus decision above; not fixed further for the same reason (avoiding a JS-measured-width dependency the grid-placement approach was adopted specifically to avoid).

Connector thickness (the line's own cross-axis dimension) — matching the old `.gain-leader`'s explicit `height: 1.5px` (`css/home/redesign.css:843`) that it replaces: at the base tier (≥768px), where the connector draws horizontally via `scaleX`, the cross-axis dimension is `height: 1.5px` (`css/home/redesign.css:843`; the length dimension, `width`, is whatever the grid cell gives it via `grid-column: 1 / -1`). At mobile, where it draws vertically via `scaleY`, the axes swap: cross-axis is `width: 1.5px`, length dimension is `height` (filled via `align-self: stretch` across the spanned rows) — so the mobile override must also flip which dimension carries the fixed `1.5px` value, not just change `grid-row`/`align-self`. Critically, this flip requires the mobile override to explicitly reset `height: auto` as well, undoing the base's unqueried `height: 1.5px` — which otherwise cascades into the mobile override unchanged and wins. `align-self: stretch` only stretches an item's block-axis size when that size is `auto`, per the CSS box-alignment spec; left unreset, the base's fixed `height: 1.5px` would override the stretch behavior entirely, and the mobile connector would render as a short 1.5px-tall stub instead of a full vertical rail through all 3 nodes. The mobile override sets both `width: 1.5px; height: auto;` explicitly (`css/home/redesign.css:894-895`), not just adding `width`. Fill color: `background: var(--ink)`, matching the old `.gain-leader`'s `background: var(--ink)` (`css/home/redesign.css:842`) it replaces — carried forward unchanged, same as the connector's thickness value above.

Within its grid cell, the connector is anchored vertically via `align-self: start; margin-top: calc(var(--gain-icon-h) / 2 - 0.75px);` (`css/home/redesign.css:844,847`; mobile's spanning connector uses `align-self: stretch` instead, per above, with the same `margin-top` still applied to inset its top edge down to node 1's dot; there is no corresponding `margin-bottom`, per the bottom-terminus decision above). The trailing `- 0.75px` term: `margin-top` positions the connector's own top edge, not its center; since the connector's own cross-axis thickness is `1.5px` (below), its unadjusted top edge would sit half that thickness (`0.75px`) below the dot's true vertical center — the same top-edge-vs-center distinction called out for the dot's own `transform: translateY(-50%)` below; this term applies the equivalent correction to the connector. Sub-pixel and imperceptible in practice, but kept for consistency with how rigorously this doc treats the same class of offset elsewhere. An earlier draft's formula also folded in a `2px +` term to account for `.gain-node`'s featured-node `border-top`, which sat inside the node's border-box above its content and pushed each icon's actual vertical center down by that extra 2px; that border-top (and the featured-node treatment it belonged to) was cut in the shipped design, so `.gain-node` has no border at all now and the connector's offset no longer needs that term — `var(--gain-icon-h) / 2` alone is the correct reference value. `.gain-node::before`'s dot needs `position: absolute; top: calc(var(--gain-icon-h) / 2); transform: translateY(-50%);` (`css/home/redesign.css:794-799`): `top: calc(var(--gain-icon-h) / 2)` alone positions the dot's own top edge at the icon's vertical midpoint, not the dot's center — the dot must also carry `transform: translateY(-50%)`, exactly the pattern the old `.gain-leader::before` used (`top: 50%; transform: translateY(-50%)`) for the identical reason — that selector no longer exists in the working tree to cite a live line number for. Without it, the dot renders roughly half its own height too low. The dot's horizontal position: `left: 0`, sitting flush with `.gain-node`'s own left edge — this is safe because `.gain-node` reserves a dedicated `padding-left: 1rem` gutter (below) that the icon, kicker, title, and copy all sit inside; the dot lives in that reserved gutter alone and no longer needs a negative offset to avoid the icon. (An earlier draft tried a small negative offset, `left: -0.35rem`, reusing the old `.gain-leader::before`'s `left: -0.3rem` precedent (no longer present in the working tree to cite a line for), scaled for the dot's ~0.5rem diameter at the time (later retuned by the density-scale-down pass to `0.4rem`, per below) — design review computed the actual resulting edge and found it insufficient: the dot's right edge landed at `-0.35rem + 0.5rem = +0.15rem`, still past the node's own `x: 0` edge, still overlapping the icon's leftmost ~2.4px. See Alternatives for why the negative-offset approach was dropped for a reserved-gutter approach instead.) `.gain-node`'s `padding-left: 1rem` insets all in-flow content (icon, kicker, title, copy) to start at `x: 1rem` instead of `x: 0`; because `.gain-node::before` is `position: absolute` and its containing block is the node's padding edge — which, since `.gain-node` has no border at all, coincides with the node's own border-box left edge — the dot's `left: 0` still resolves to the node's true outer left edge, unaffected by the new padding. With the dot's `0.4rem` diameter sitting at `x: 0` to `x: 0.4rem` and content now starting at `x: 1rem`, there's a verified `0.6rem` (9px) gap between the dot's right edge and the icon's left edge — computed clearance, not another eyeballed offset. This also makes an earlier column-gap-clearance constraint (a prior draft required `.gain-graphic`'s column-gap be wide enough to keep the dot's negative offset from colliding with the previous node's content) unnecessary and incorrect under this approach: the dot now lives entirely inside its own node's reserved gutter and never extends into the gap between grid columns, so column-gap sizing (still an open implementer value, below) carries no dot-clearance constraint.

Stacking order alone is not sufficient here, and an earlier draft overstated what it achieves: `.gain-connector-primary` gets `z-index: 0`; `.gain-node` gets `z-index: 1` (in addition to `position: relative`) — this correctly makes `.gain-node`'s own painted pixels render above the connector wherever they overlap, but z-index only governs paint order between elements that actually have opaque pixels at a given point; it doesn't make anything occlude anything else on its own. This also relies on a specific, unstated CSS Grid behavior: `.gain-connector-primary` is a direct child of `.gain-graphic`'s grid (a sibling of `.gain-nodes`) and never gets an explicit `position` value anywhere in this doc, so it remains `position: static` by default — per the CSS Grid spec's carve-out (and confirmed current cross-browser behavior), `z-index` still applies to a `position: static` grid item exactly as if it were `position: relative`, so the stacking rule above works without needing `position` set on the connector element too; a silent load-bearing assumption, not an oversight, worth stating given how exhaustively this doc otherwise justifies comparable minutiae. Every icon is stroke-only with no fill and no background (per the shared icon system above), so at the base tier — where the connector is a continuous horizontal line spanning the full row width (`grid-column: 1 / -1`) at the icon's own vertical center — the line would still visibly show through each icon's open linework and negative space even with the z-index rule in place, since there's nothing opaque there for the z-index ordering to actually hide the connector behind. Fix: `.gain-icon` also gets `background: var(--paper)` — matching `.gains`'s own page background (the section carries the `chapter-grid` class, `index.html:215`, whose `72px` blueprint grid-line pattern this locally occludes, the same established local-occlusion precedent already used for `.arcade-board`/`.role-card`, see Join below). Because `.gain-icon` is already a fixed `--gain-icon-h` square sitting directly on top of the connector's own y-band, this gives the z-index rule actual opaque pixels to work with: the connector segment passing behind each icon is now genuinely covered, not just nominally "behind" a transparent SVG. At mobile, the connector (`x: 0`–`1.5px`) and all node content (`x: 1rem`+, per the `padding-left` gutter above) never share an x-range at all — the gutter reservation alone fully separates them there. This `background: var(--paper)` fix is specifically a base-tier fix, where the connector's horizontal line genuinely crosses every node's icon; it has no mobile-specific role.

Animated via `scaleX` (base tier, `transform-origin: left center`) or `scaleY` (mobile, `transform-origin: top center`) — the same technique already used for the old `.gain-leader` (pre-redesign code, no longer present in the working tree to cite a live line number for; the static CSS for `.gain-leader` itself had no transform (that selector no longer exists in the working tree to cite a live line number for) — the animation lived in the JS file), applied to the single grid-placed `.gain-connector-primary` element instead of one leader per note. Two `gsap.matchMedia()` buckets, one per tier, each animating `.gain-connector-primary`: `mm.add("(min-width: 768px)", ...)` (`scaleX` draw) and `mm.add("(max-width: 767px)", ...)` (`scaleY` draw) — `js/animations.js:153,163`. An earlier draft split desktop and tablet into two separate matchMedia buckets on the theory that the connector's shape genuinely differed between them (one line vs. two segments); once desktop and tablet were unified into one shared 3-column grid with a single connector element, that distinction went away, and this ended up being the same `768px`/`767px` split every other `gsap.matchMedia()` bucket in this file already uses (`js/animations.js:100,122` for comparison) — not a new boundary value, unlike the earlier draft's rejected `1024px`/`1023px` idea. No `invalidateOnRefresh` needed — the grid-placement approach needs no JS-computed distance at any breakpoint, unlike the `.builds` gallery's `getDistance()` precedent (`js/animations.js:129-140`) it was originally modeled on.

**Node entrance animation: reuse the existing shared `reveal()` helper, not a bespoke per-row stagger.** GSAP cannot directly target a `::before` pseudo-element (no DOM node to grab), so the dot's reveal was always going to inherit visibility from its parent `.gain-node`'s own opacity tween regardless of how that tween was triggered. `.gain-node` is simply added to the existing shared `reveal()` call (`js/animations.js:187-189`: `reveal(".builds-head, .gains .section-title, .join-head, .role-card, .arcade-head, .arcade-game, .gain-node")`) — the same proven per-element independent-scroll-reveal pattern already used for `.role-card` and others (`js/animations.js:174-185`). Each node reveals independently as it individually scrolls into view, regardless of total container height at any breakpoint. Because the dot is a child of `.gain-node`, it slides along with its parent during that ~0.9s `reveal()` tween — meaning each node's dot is transiently offset from the connector line's rest position for the duration of its own entrance animation, snapping into final alignment only once that tween completes. The same `reveal()` tween's `opacity: 0 → 1` also means `.gain-icon`'s `background: var(--paper)` occlusion backdrop (above) is only fractionally opaque for that same ~0.9s window, since animating a parent's `opacity` composites its entire stacking context as one layer — so the connector can transiently show through the icon during a node's own entrance too, the same class of transient artifact as the dot's offset, accepted for the same reason: it resolves to the correct rest state once the tween completes, and isn't a rest-state bug. Accepted: the connector itself is mid-draw or already drawn during the same general viewport-entry window, and a brief transitional misalignment during an entrance animation is a normal, expected side effect of independently-triggered per-element reveals, not a rest-state bug — called out here so it isn't mistaken for a failure if observed mid-scroll (the verification checklist's dot-centering check, below, is a rest-state check, not a mid-transition one). The connector's own draw is a separate, purely decorative accent line with its own `ScrollTrigger` (`trigger: ".gain-graphic", start: "top 75%"`) — not required to be frame-synced to individual node reveals; an intentional scope simplification. This does reintroduce a milder version of the same off-screen concern at mobile: `.gain-connector-primary`'s single continuous line spans all 3 stacked nodes off that same container-level trigger, which can fire while node 3 is still off-screen — so the "connector finishes drawing before the last node is on-screen" effect can occur there. Accepted as-is: GSAP's default `toggleActions` doesn't replay a completed tween, so this is a missed decorative flourish, not a broken state.

**Reduced-motion / pre-hide: no new CSS pre-hide handling is being introduced.** The connector needs opposite-axis `scale` values per breakpoint, which one non-breakpoint-scoped pre-hide rule can't express correctly, and nesting it inside width media queries adds complexity for a small gain. Simpler, more consistent choice: don't add pre-hide handling for gains at all. Every other `reveal()`-driven element on this site today (`js/animations.js:187-189`: `.builds-head`, `.join-head`, `.arcade-head`, `.arcade-game`, and `.role-card` itself) already has this same brief pre-JS-load flash and no pre-hide treatment; only the hero gets one. Accepting the same site-wide-standard minor flash for the new gains elements is consistent with existing convention, not a regression, and out of scope to fix here.

**Join: role-cards get icons + a real card body.** Title/subhead/CTA (`.join-head`, `index.html:338-353`) unchanged. Each `.role-card` gets a `.role-icon` (one of the 3 new icons) placed above the existing `<h4>`/`<p>`, with an explicit `margin-bottom` between `.role-icon` and the `<h4>` that follows it (exact value an implementer call, but must be explicitly set, per the sitewide margin-reset issue described above). The existing `border-top: 2px solid var(--ink); padding-top: 1.25rem;` (formerly at `css/home/redesign.css:934-937`, pre-redesign; no longer present in the working tree) is removed entirely, not layered under new declarations — replaced wholesale with: background `#fff`, `border: 1px solid var(--slate)` (`var(--slate)` — `#42536b`, `css/home/redesign.css:10` — not `var(--line)`; see below), corner radius smaller than builds' 24px (12–16px, exact value open), padding on all four sides.

The border-color choice replaces two earlier attempts that design review found didn't actually work: `var(--line)` (`#d7e0ec`) computed to roughly 1.2–1.3:1 contrast against both the white card fill and the page's `var(--paper)` (`#f7f9fc`) background — visually close to imperceptible; a follow-up attempt relied on `box-shadow: rgba(0, 45, 114, 0.08)` as the primary distinguishing signal instead of border color, but that computed to roughly 1.16:1 against the page — the same magnitude of failure, just relocated to a property that's harder to eyeball-check, and one that disappears entirely under forced-colors/Windows High Contrast mode (per the CSS Forced Colors spec, `box-shadow` computes to `none` there; a colored border at least gets remapped rather than vanishing). `var(--slate)` at 1px computes to roughly 7.4:1 contrast against `var(--paper)` (and roughly 7.8:1 against the white card fill) — genuinely visible on a real display, not just numerically passing. (Whether WCAG 1.4.11's 3:1 guidance formally applies here at all is arguably debatable — that success criterion targets interactive UI components and graphical objects required to understand content, and this card is neither interactive nor is its boundary required to understand the heading/paragraph inside it — but a real, visibly-distinct border is the actual design goal regardless of which SC technically governs it, and costs nothing extra to get right.) A subtle `box-shadow` (`0 2px 8px rgba(0, 45, 114, 0.08)`, exact alpha/blur an implementer call) can still be layered on as secondary depth polish, but the border color is what does the actual work of making the card read as distinct from the page.

`.arcade-board` (`css/home/redesign.css:1360-1368`) is actually the first light card already sitting on the gridded blueprint background — not `.build-art`, whose card sits on a dark background and isn't directly analogous. The white fill in both `.arcade-board` and this new `.role-card` fully occludes the `72px` blueprint grid locally in that area. `.arcade-board`'s own border currently uses `var(--line)` (`#d7e0ec`) — the exact color this doc's contrast math above proves computes to roughly 1.2–1.3:1, near-invisible — a pre-existing low-contrast border this doc doesn't fix (out of scope; `.role-card` is a separate element) but flags here so it isn't mistaken for a deliberate precedent to match. `.role-card`'s own border deliberately uses `var(--slate)` instead, for the contrast reasons above. No hover/focus/pointer-cursor treatment is planned — these cards aren't links or buttons. Styling `.role-card` with a border/radius/shadow does give it a visual "card" affordance despite being non-interactive, which carries a minor risk of implying clickability it doesn't have; accepted, since `.build-art`'s image card (`css/home/redesign.css:676-681`) is the same non-interactive "card"-styled precedent already on this page, and the visual-distinction goal outweighs this minor affordance ambiguity. No new animation needed — `.role-card` already sits in the shared `reveal()` fade-up list; that keeps working unchanged.

## Alternatives (considered and rejected)

- **Hand-drawn/illustrated SVG diagram for gains, now.** Rejected for this pass — sequenced explicitly as "icon cards first, hand-drawn diagram later," a bigger asset/illustration effort deferred to a future redesign pass.
- **Keep the blueprint ink-fill/leader-line motif, just re-skin.** Rejected — breaking from it was explicitly approved; the stroke/fill double-text-layer trick was also identified as part of the "movement" complaint.
- **Icon font or external SVG icon library.** Rejected — adds a build/asset dependency this vanilla Vite site doesn't otherwise have. Hand-authored inline SVG keeps everything in code.
- **Per-row ScrollTrigger retained, just fewer rows.** Rejected — the scroll-fatigue complaint is about the per-row-scrub animation model itself, not row count.
- **Restyle `.role-card` only (bg/border), skip icons.** Rejected — "icon driven first" was chosen explicitly over a plain re-skin.
- **SVG `<path>`/`<line>` with `stroke-dashoffset` for the connector.** Rejected — the old `.gain-leader` this replaces was always a plain div/line, not SVG; reusing the same div+`scaleX`/`scaleY` technique avoids introducing a second animation primitive.
- **`<ol>` for `.gain-nodes`.** Switched to `<ul>` — an ordered list asserts strict sequence to assistive tech, conflicting with this section's "loosely connected" framing. Caveat: `.gain-list` (being replaced) already has `list-style: none`, and Safari+VoiceOver is known to strip the implicit list role when `list-style: none` is set; separately, whether an ancestor with `display: contents` still exposes a `<ul>`'s implicit list role to its `<li>` children at all has also had inconsistent cross-browser behavior historically. Both risks share the same standard, trivial remedy: `.gain-nodes` gets an explicit `role="list"` attribute, restoring list semantics to assistive tech regardless of `list-style` or `display: contents` — applied directly in the markup (see Detailed Implementation), not left as an open question. A screen-reader smoke test during implementation should still confirm this behaves as expected across browsers/AT combinations, since the fix is applied preemptively rather than verified against a known failure first.
- **Two separate `gsap.matchMedia()` buckets for desktop and tablet (on the theory that they need genuinely different connector geometry).** Rejected once desktop and tablet were unified into one shared 3-column grid — with one connector element and one shape at that tier, desktop and tablet only ever needed the single shared `(min-width: 768px)` bucket that shipped.
- **`invalidateOnRefresh: true` on the connector's ScrollTrigger.** Considered, then dropped — the grid-placement approach needs no JS-computed distance at any breakpoint.
- **A featured/accented node (originally node 1, "course credit") with full visual parity for the rest.** An earlier draft gave node 1 a distinct `border-top: 2px solid var(--ink)` via a `.gain-node--featured` modifier class, reasoning that course credit was the section's strongest recruiting hook and shouldn't look identical to the other nodes. A later revision cut this along with node 1 itself — the shipped design has 3 nodes with full visual parity and no featured treatment, no `.gain-node--featured` class, and no accent border anywhere in `.gain-node`.
- **`.gain-connector` absolutely positioned inside `.gain-graphic`, dots aligned via independently-computed matching `top` offsets.** Rejected — no real DOM relationship for a second connector element to "be sibling to," and no way for the mobile connector to know its own total length. Replaced with the CSS Grid approach above.
- **Letting `.gain-node` auto-place in the grid while only the connector gets explicit placement.** Rejected — per the CSS Grid spec, fully-definite items reserve cells before auto-placed items are positioned; this would push nodes into a new implicit row instead of sharing a row with the connector. Fixed by giving every grid item explicit placement, on every tier.
- **Three mutually-exclusive, individually-scoped media queries for desktop/tablet/mobile, with no shared base.** Rejected after review — a "hidden unless a specific tier turns it on" rule needs an unqueried base to live in, which three disjoint queries don't provide. Restructured to match the sitewide convention (unqueried default base, `max-width` overrides) that every other breakpoint in this file already uses; a later revision went further and merged desktop and tablet into that one shared base entirely, leaving just the base plus a single `max-width: 767px` mobile override.
- **Ellipsis/nowrap truncation on `.gain-node-copy`.** Rejected — the actual final copy doesn't fit on one line at either tier's column width; would silently clip real sentences. Copy wraps normally with a fixed `min-height` reservation instead.
- **Bespoke per-row `.gain-node` stagger-in tied to the connector's own `ScrollTrigger`.** Rejected — risked off-screen entrance completion at tall tablet stacks, and GSAP can't animate `::before` anyway. Replaced with adding `.gain-node` to the existing shared `reveal()` helper.
- **Adding gains elements to the hero's `prefers-reduced-motion: no-preference` pre-hide block.** Rejected — the connector needs opposite-axis `scale` values per breakpoint, which one non-breakpoint-scoped pre-hide rule can't express. Dropped entirely, consistent with every other `reveal()`-driven element on the site already accepting the same minor pre-JS flash.
- **`box-shadow` as the primary distinguishing signal for `.role-card`, in place of a flat border/fill color.** Rejected after review — computed contrast (~1.16:1 against the page) is the same magnitude of failure as the flat-color approach it was meant to replace, just relocated to a property that's harder to formally verify, and one that disappears entirely under forced-colors mode (unlike a colored border, which at least gets remapped). Replaced with a `var(--slate)` border (real ~7.4:1 contrast), with `box-shadow` kept only as secondary depth polish.
- **`var(--line)` as `.role-card`'s border color.** Rejected — computed contrast against both the card fill and the page background (~1.2–1.3:1) is far under WCAG 1.4.11's 3:1 guidance and close to imperceptible in practice. `var(--slate)` instead.
- **A separate desktop/tablet breakpoint split (at various points drafted as `1025px/1024px` or `1024px/1023px`).** Rejected — doesn't match the sitewide convention (`max-width: 767px` is the only breakpoint value used elsewhere in this file). Realigned to an unqueried default base (≥768px) plus a single `max-width: 767px` override, once desktop and tablet were unified into one shared grid.
- **Hardcoding the icon-height value separately in `.gain-icon`, the dot's `top` calc, and the connector's `margin-top` calc.** Rejected after review — three independent literals drift silently if the icon size is ever tuned later. Backed by one CSS custom property, `--gain-icon-h`, referenced in all three places instead.
- **Fluid `clamp()`-based icon sizing, matching the site's headline type scale.** Rejected — a small, fixed-size decorative UI glyph doesn't carry the same legibility-driven need for fluid scaling that running headline text does; responsiveness comes from the grid reshaping per tier instead. One fixed `--gain-icon-h` value at all tiers.
- **`top: 50%`-style dot centering without a matching `transform`.** Rejected after review — `top` (or a `top: calc(...)` offset) alone positions an absolutely-positioned element's own top edge, not its center; without `transform: translateY(-50%)`, the dot renders roughly half its own height too low, breaking the exact icon/dot/connector alignment this doc otherwise obsesses over. The old `.gain-leader::before` this replaces already paired `top: 50%` with `transform: translateY(-50%)` for this reason; the new calc-based offset keeps that same transform.
- **Capping the mobile connector's bottom edge exactly at node 3's dot via a computed `margin-bottom`.** Rejected after review — node 3's content height (and thus the distance from the grid area's bottom line back up to its dot) varies with wrapped copy length, so no single fixed `margin-bottom` calc can land precisely on it the way `margin-top` lands on node 1's dot (whose distance from the grid area's *top* line is constant). Accepted instead: the connector runs past node 3's dot to the bottom of its content block, since its role is a continuous rail through the sequence, not a precise joint-to-joint line.
- **Letting `.gain-icon`/`.role-icon`'s width be picked independently of height.** Rejected after review — a non-square wrapper undermines the square-viewBox mandate one level up, letterboxing the icon inside a mismatched box even though the icon artwork itself is square. Width pinned equal to height in both cases.
- **Leaving the mobile connector's `height` at the base tier's `1.5px` and relying on `align-self: stretch` alone to fill the row span.** Rejected after review — `align-self: stretch` only stretches an item's size on an axis whose size is `auto`; the base's explicit `height: 1.5px` cascades into the mobile override unless reset and wins over `stretch`, producing a short fixed-height stub instead of a full-height rail. Mobile override now explicitly resets `height: auto` alongside setting `width: 1.5px`.
- **Small negative dot offset alone (`left: -0.35rem`), reusing the old `.gain-leader::before` precedent's `left: -0.3rem` (`css/home/redesign.css:807`) scaled for the new dot's ~0.5rem diameter.** Tried, then rejected after review — the old precedent's geometry doesn't transfer: `.gain-leader::before`'s dot had nothing else nearby to collide with, but here the icon sits flush at the same `x: 0` edge. Design review computed the actual resulting edge: `-0.35rem + 0.5rem` diameter `= +0.15rem`, still past the node's own `x: 0` edge, so the dot still overlapped the icon's leftmost ~2.4px — the offset didn't actually fix the collision it was meant to fix. Replaced with a `padding-left: 1.25rem` gutter reserved on `.gain-node` itself (see Technical Plan): the dot goes back to `left: 0`, but now safely inside that reserved gutter, with all content (icon/kicker/title/copy) starting at `x: 1.25rem` instead of `x: 0` — a verified `0.75rem` (12px) gap between the dot's right edge and the icon's left edge, not another eyeballed offset.
- **`z-index` alone to make the connector render behind each node's icon.** Rejected after review — every icon is stroke-only with no fill/background, and z-index only orders paint between elements that have opaque pixels; it can't make a transparent SVG occlude anything. Fixed by also giving `.gain-icon` an opaque `background: var(--paper)` backdrop matching the page background, so the z-index ordering has actual pixels to occlude the connector with — see Technical Plan's stacking-order paragraph.
